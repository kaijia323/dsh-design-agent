## 七、发现的问题清单

### 7.1 [环境 · 需要处置] 运行中的 DSH 还是旧模块代，界面上批注契约仍活着

**现象**：对正在跑的 DSH（`http://127.0.0.1:3080`）发一次**只读**的 `readProject`，回来的 body 里仍然有 `comments`：

```
HTTP 200 | ok = true
响应顶层 key: ["ok","project","frames","tokens","comments","selection","exists","recovered","designDir"]
project 顶层 key: ["version","viewport","tokens","frames","comments","selection","updatedAt","updatedBy"]
响应/工程里是否出现 comments 键: {"body.comments":true,"project.comments":true}
```

**为什么能断定是模块代数问题而不是代码问题**：冻结版 `src/host/design-project.js` 里已经没有任何 `comments` 字样（AC1 的 grep 是 0），磁盘上的 `.design/design.json` 也没有 `comments` 字段（§4.3）。能吐出这两个键的只可能是**进程里加载的旧模块**。host 是普通 ESM，DSH 的 loader 不带 cache-bust，改 host 代码必须重启 profile 才生效（`README.md` 与 `scripts/post-restart-check.mjs` 的注释都写了这一点）。

**影响**：代码清干净了，但**正在运行的这个实例**还没有——用户在界面上触发的 `design_status` 仍会返回 `comments`。要看新契约，得重启 profile。我没有重启（会打断用户），所以这一条只能报到这里。

## 八、我没能验到的部分

1. **真实 GUI 交互链路**：点元素 → @ 式引用胶囊 → 输入框展开、切屏、落地到项目，这些都没有在真实 DSH 界面里跑过。两个原因：一是运行中的 host 是旧模块代（§7.1），二是重启用户的实例会打断他正在做的事。这一条只能由 Lead/用户在重启后补验。
2. **client.js 作为浏览器 bundle 的整体加载**：仓库没有 `node_modules`、client.js 依赖宿主注入的 React 等运行时，我没有把它加载起来跑过。我只做了 `node --check` 与 PROBE_JS 的文本级提取校验——**组件渲染路径（Preview / iframe 挂载 / 引用胶囊）零覆盖**。
3. **探针是复刻而非调用**：夹具用的是我照抄的 `withProbe()`。如果将来注入规则改了，我的夹具不会跟着变（本次比对的是同一份 PROBE_JS 源文本，注入规则逐行照抄，风险有但不为零）。
4. **真实历史批注数据的去向**：我只在临时目录构造了「带 comments 的旧 design.json」验证读兼容。**真实工作区那份 design.json 在我接手前就已经没有 comments 字段**，而 `.design/` 不进版本控制、没有可比基线——因此我**无法证明也没有证伪**「验收期留下的那 3 条历史批注是被谁、什么时候丢掉的」。我没有在真实工作区故意放一份旧文件去测（怕污染用户数据）。
5. **三屏的视觉正确性**：只做了「按声明尺寸渲染 + 元素数 + 控制台无错 + 1 张截图」这一层，没有做像素级/版式比对（那不属于本次改动的验收范围）。
6. **`.playwright-mcp/` 里的 805 行命中**：旧界面的 HTML 快照等证据文件，按裁定不动，我没有逐条读。它们里含旧 UI 文本（例如「批注（N）」按钮），不属于代码残留。
7. **`specs/` 的业务约束**：仓库里没有独立的 spec validator 脚本，我只验了「两份 YAML 仍可解析（顶层 `spec`）」与段首注记的位置，没有校验规格正文里的业务约束是否自洽。
8. **重启后的效果**：§7.1 只证明了「现在是旧的」，没有证明「重启后一定变新」。这需要在重启后再跑一次同一个只读探针（命令见 §7.1），我没有做。
